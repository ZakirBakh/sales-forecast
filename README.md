# Прогноз продаж розничных банковских продуктов на 4 недели вперёд

Финальный проект курса Data Science.

Я работаю аналитиком в банке и слежу за продажами основных розничных продуктов. В этом проекте я построил модель, которая прогнозирует **число продаж (новых договоров) на каждый из 28 следующих дней** по 15 продуктовым рядам: карты, кредиты и срочные депозиты. Такой прогноз помогает планировать продажи, нагрузку на отделения, лимиты выдач и потребность в фондировании.

| | |
|---|---|
| **Проблема** | План продаж обычно делают вручную по прошлым месяцам. Так плохо учитываются праздники, длинные каникулы, пик продаж по понедельникам и тренды отдельных продуктов |
| **Кому полезно** | аналитику или менеджеру розничного блока: раз в 4 недели он получает прогноз на ближайшие 28 дней |
| **Данные** | выгрузка из хранилища банка за 01.01.2023–30.09.2026 по дням, 15 рядов, ~18,5 тыс. наблюдений. В репозитории лежит **обезличенная версия** (см. ниже) |
| **Тип задачи** | регрессия на временных рядах: по истории и календарю предсказать продажи за день |
| **Модель** | одна модель LightGBM на все ряды, 37 признаков, гиперпараметры подобраны в Optuna |
| **Метрика** | WAPE = Σ\|факт − прогноз\| / Σ факт — доля ошибки от объёма продаж |
| **Демо** | приложение на Streamlit: прогноз по любому продукту, сценарий ограничения выдач, качество на тесте, выгрузка в CSV |

## Результаты

Я сравнивал модель с простым прогнозом без ML (бейзлайном): «среднее за последние 4 известные недели по тому же дню недели». Метрика — дневной WAPE, меньше — лучше.

| проверка | модель | бейзлайн | разница |
|---|---|---|---|
| валидация (апрель–июнь 2026) | **0,224** | 0,372 | −40 % |
| тест (июль–сентябрь 2026), все дни | **0,317** | 0,359 | −12 % |
| тест без разового события¹ | **0,226** | 0,274 | −18 % |
| скользящий бэктест, 13 прогнозов по 28 дней (среднее) | **0,316** | 0,468 | −32 %, модель лучше в 11 из 13 |

¹ 2–8 сентября 2026 г. банк массово выпустил виртуальные карты нерезидентам: за неделю больше половины продаж этого ряда за весь квартал. По истории такое не предсказать, поэтому я показываю метрики с этим событием и без него.

**Главные выводы:**
* Основной выигрыш модели даёт **календарь**: праздники, новогодние и майские каникулы. Бейзлайн «как 4 недели назад» переносит обычные продажи на праздничные дни, а модель знает, что в праздник продаж нет.
* На горизонте **месяца** модель бейзлайн не обгоняет: в месячной сумме ошибки по дням взаимно гасятся. Модель лучше всего подходит для дневного и недельного планирования.
* Хуже всего прогнозируются продукты, которые продаются кампаниями: карты нерезидентам, пенсионные и социальные карты, зарплатные карты.

Все расчёты и комментарии — в ноутбуках `notebooks/01_EDA.ipynb` и `notebooks/02_Modeling.ipynb`.

## Как запустить

### 1. Установка (один раз)

Нужен Python 3.10 или новее. Откройте терминал в папке проекта:

```bash
python -m venv .venv

# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

Установка библиотек занимает 5–10 минут.

### 2. Демо

```bash
streamlit run app/app.py
```

Откроется браузер на `http://localhost:8501`. Модель уже обучена и лежит в `models/`, поэтому демо работает сразу.

Что можно посмотреть:
1. **Кредит → Онлайн кредит**: история и прогноз на 28 дней. Видны выходные (продаж нет), пик по понедельникам и праздники.
2. Включить **«Сценарий: ограничение выдач кредитов»**: прогноз падает — так можно оценить последствия решения об ограничении выдач.
3. Вкладка **«Качество на тесте»**: факт, прогноз модели и бейзлайна за июль–сентябрь 2026.
4. **Карта → Все продукты группы**: прогноз по продуктам и кнопка «Скачать прогноз (CSV)».

### 3. Ноутбуки

```bash
jupyter notebook notebooks/
```

Результаты уже сохранены в ноутбуках, их можно просто читать. Чтобы пересчитать: **Kernel → Restart & Run All**. `02_Modeling` считается 3–4 минуты.

### 4. Полный пересчёт модели

```bash
python -m src.pipeline              # 3–5 минут
python -m src.pipeline --trials 20  # быстрее: меньше итераций подбора параметров
```

Что происходит:
1. загрузка данных и проверка, что в каждом ряду нет пропущенных дней;
2. построение 37 признаков;
3. разбиение по времени: обучение — до 31.03.2026, валидация — апрель–июнь 2026, тест — июль–сентябрь 2026;
4. бейзлайны и 4 модели, сравнение на валидации;
5. подбор гиперпараметров LightGBM в Optuna (40 итераций);
6. переобучение на обучении + валидации и **одна** проверка на тесте;
7. скользящий бэктест: 13 прогнозов по 28 дней;
8. обучение итоговой модели на всех данных и прогноз на 28 дней вперёд.

Результаты сохраняются в `reports/`, `models/` и `data/processed/`. Случайность зафиксирована (`random_state = 42`), поэтому результаты повторяются.

## Как я готовил данные

**Источник:** витрины хранилища банка (MS SQL) по картам, кредитам и депозитам. Витрины помесячные: договор повторяется в каждом месяце, пока он активен.

**В SQL** (папка `sql/`):
* каждый договор беру **один раз** — из среза за месяц открытия. Иначе один кредит посчитался бы около 12 раз;
* продажа карты — это **новый карточный договор**, а не выпущенная карта. Перевыпуски и дополнительные карты продажами не считаю;
* исключил продукты сотрудников банка, тестовые продукты и депозиты на индивидуальных условиях;
* выгрузка по дням, дни без продаж — с нулём.

**При сборке рядов:**
* сотни карточных продуктов и десятки кредитных и депозитных сгруппировал в 16 рядов по смыслу: платёжная система, зарплатные, пенсионные и социальные, кредитные, нерезиденты, виртуальные и т.д. Ряд «Архивные депозиты» в модели не используется: в нём только закрытия;
* если банк заменил один продукт другим (например, старый экспресс-кредит — новым кредитом наличными), я объединял их в один непрерывный ряд. Иначе модель увидела бы ложное падение продаж;
* итоги сверил с исходной выгрузкой.

**Особенности данных и как я их учёл:**

| особенность | что сделал |
|---|---|
| с 16.10.2023 по 04.02.2024 банк ограничивал выдачи кредитов из-за нехватки ресурсов | добавил признак-флаг этого периода; в оценке период не участвует |
| в выходные продаж почти нет, в понедельник — в 1,7–2,2 раза больше среднего | признаки дня недели, нерабочего дня, числа выходных подряд перед датой |
| праздники Кыргызстана и ещё 5 нерабочих дней банка, которые я нашёл по данным | календарь в `src/calendar_kg.py` |
| разовые массовые выпуски карт | список `ONE_OFF_EVENTS` в `config.py`: такие дни убираются из обучения, но остаются в оценке |
| копилка запущена 12.05.2025 | ряд начинается с первой продажи |

### Обезличивание

Реальные данные банка публиковать нельзя, поэтому в репозитории лежит обезличенная версия (`src/mask_data.py`):
* каждый ряд умножен на свой секретный коэффициент (0,55–0,8 или 1,25–1,6), суммы — ещё на один общий коэффициент;
* ставки и сроки продуктов убраны;
* даты, нулевые дни, недельный профиль, праздники и всплески сохранены, поэтому выводы анализа и сравнение моделей те же.

Все числа в этом README и в ноутбуках посчитаны на обезличенных данных.

## Почему я сделал именно так

* **Признаки только из данных старше 28 дней.** Тогда одна модель честно прогнозирует любой из 28 дней вперёд и никогда не «подсматривает» в будущее.
* **Одна модель на все ряды.** Маленькие продукты перенимают общие закономерности (праздники, понедельники) у больших, а поддерживать одну модель проще, чем 15.
* **WAPE, а не MAPE.** В данных много нулевых дней, MAPE на них делится на ноль. WAPE учитывает ошибку пропорционально объёму продаж.
* **Разбиение строго по времени и бэктест.** Случайное разбиение для временных рядов завышает качество. Бэктест показывает, что выигрыш устойчивый, а не случайный.
* **Модель выбрана по валидации, а не по тесту.** Иначе тестовая оценка перестала бы быть честной.

## Ограничения и что можно улучшить

* Модель не знает о плановых кампаниях и массовых выпусках карт. Улучшение: добавить календарь кампаний как признак.
* После длинных выходных модель недооценивает всплеск продаж. Улучшение: отдельные признаки или модель для понедельников.
* Ставки и условия продуктов в модель не входят. Улучшение: сценарий «что будет, если изменить ставку».
* Новые продукты и замены требуют ручного объединения рядов.
* Данные одного банка и одной страны.
